# 设计哲学

> 状态：草稿，仍在构思中。本文回答"为什么这么做"；`architecture-revision.md` 回答"怎么做"。

## 定位

**TokenMaw 的目标是成为能力最强、结果最可信的 coding agent。**

能力是目的。简单是手段：用最薄的代码，换来更好的行为。

## 原则

### 1. 能力第一

- 用户要的是"交给它，事情做成"：完成率高、能自己验证、失败后能恢复、长任务不跑偏。
- 其他一切，包括架构、简洁、功能对齐，都为这一条服务。
- 与别的产品对比时，比的是真实任务上的表现，而不是功能清单。

### 2. 可信：完成必须有证据

- 能力的前提是结果靠得住。声称完成之前，系统要能指出验证过什么：文件读回、测试结果、命令退出码。
- 没有成功的工具结果，就不能说"已保存""已修复"。
- 这条由 Runtime 强制检查，Agent Spec 无法绕过。

### 3. 简单是手段：薄 Runtime，厚文档

> 假设（待验证）：agent 行为的提升，主要来自文档，而不是更多代码。

- **Runtime 保持薄而稳。** 只做不可绕过的机制：执行、工具、安全边界、持久化、并发。每个新机制都要回答"去掉它会怎样"，答不出来就不加。
- **能力在文档层生长。** Agent Spec、skills、`AGENTS.md`、工作流手册，是改进行为的主要杠杆：改得快、不用发版、项目和用户可以自己覆盖、可以分享。
- **文档写目标和判断标准，少写步骤。** 补丁式规则会随模型升级而过时，甚至碍事。
- **这个假设的边界：**
  - 文档只能引导，不能强制。不能出错的保证，必须留在 Runtime（见原则 2）。
  - 文档的好坏靠评测验证，不靠感觉（见原则 6）。

### 4. 复杂度放对地方：核心简单，工具可以复杂

- **核心**（agent loop、调度、持久化）保持简单：人人依赖它，越简单越可靠、越好调试。
- **工具能力可以复杂，这是拉开差距的地方。** 编辑容错、搜索质量、LSP 诊断、长输出处理、沙箱执行，做深了就是壁垒。
- 约束：
  - 接口简单，内部复杂。模型看到的工具要少而清晰，容错与回退藏在实现里。
  - 复杂度必须被评测证明；没提升完成率的复杂工具是负担。
  - 工具要与核心隔离：一个工具崩溃或卡住，不能拖垮 agent loop。

### 5. 机制归框架，策略归 Markdown

- Runtime 里不出现 router、planner 之类的角色语义。
- **判断标准：** 如果某条规则被项目级 spec 覆盖后，会让用户丢数据或被误导，它就是机制，必须进 Runtime；否则是策略，留给文档。

### 6. 用数据说话

- 没有基线数据的"改进"，不算改进。
- 工具、prompt、文档、上下文策略的改动，都应该能在评测里看到效果。
- 这也是"厚文档"路线的前提：没有评测，就无法知道哪段文档有用、哪几条规则互相打架。

### 7. 防 agent 犯错，不防用户

- 不加确认弹窗，用户运行 yolo 就是 yolo。
- 但对意外破坏做硬防护：覆盖未读过的文件、symlink 逃逸、并发写冲突、会话丢失。

## 原则冲突时

- **能力 > 简单。** 简单只是手段。如果某个机制确实能带来可验证的能力提升，就值得加，但要用最简单的方式实现。
- **可信 > 灵活。** 为了让结果可信而必须强制的检查，不留给 spec 绕过。

## 机制与策略的划分（待核对）

| 属于机制（Runtime 强制） | 属于策略（文档可调） |
|---|---|
| 写文件后读回验证、不得空口宣称完成 | agent 的角色和职责描述 |
| 路径边界、symlink 防护、原子写、文件锁 | 使用哪个模型 |
| 会话与实例的持久化、崩溃恢复 | 何时委派、委派给谁、是否并行 |
| 并发、超时、递归深度上限 | 如何汇总和回应用户 |
| 工具授权与全局策略 | 调试、测试、git 等工作方法（skills） |

**已知偏差：** `agents/main.md` 里有一些属于左列的硬保证（如"写完必须读回验证"），目前只靠 prompt 约束，项目级 spec 整体覆盖后会丢失。后续应迁到 Runtime 检查。
