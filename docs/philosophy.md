# 设计哲学

> 状态：草稿，仍在讨论中。本文回答"为什么这么做"；`architecture-revision.md` 回答"怎么做"。
> 标注"待定"的地方是尚未做出的决定，不是结论。

## 定位

**TokenMaw 的目标是成为能力最强、结果最可信的 coding agent。**

能力是目的。简单是手段：核心保持很薄，能力在外围生长。

## 原则

### 1. 能力第一

- 用户要的是"交给它，事情做成"：完成率高、能自己验证、失败后能恢复、长任务不跑偏。
- 其他一切，包括架构、简洁、功能对齐，都为这一条服务。
- 与别的产品对比时，比的是真实任务上的表现，而不是功能清单。

### 2. 核心薄，能力厚

复杂度不是要全局压低的东西，而是要放对地方。

| 层 | 复杂度策略 | 原因 |
|---|---|---|
| **核心**（agent loop、调度、持久化、授权执行） | 保持简单 | 人人依赖它，越简单越可靠、越好调试 |
| **工具能力** | 可以复杂，这是拉开差距的地方 | 编辑容错、搜索质量、LSP 诊断、长输出处理，做深了就是壁垒 |
| **文档**（Agent Spec、skills、`AGENTS.md`） | 靠评测约束 | 容易膨胀、互相冲突 |

- 接口简单，内部复杂：模型看到的能力要少而清晰，容错与回退藏在实现里。
- 复杂度必须被评测证明；没提升完成率的复杂能力是负担。
- 能力与核心隔离：一个能力崩溃或卡住，不能拖垮 agent loop。
- 文档写目标和判断标准，少写步骤。补丁式规则会随模型升级而过时，甚至碍事。

> 假设（待验证）：agent 行为的提升，主要来自文档和工具，而不是更多核心代码。

### 3. 统一的能力（capability）

Skill 和 Tool 本质上是同一种东西：**一个被声明、被发现、按需加载的能力**。区别只在有没有可执行的部分。

```md
---
description: 何时使用（只有这一行常驻上下文）
params: ...        # 可选：有参数就是工具，没有就是纯指引
run: ./check.sh    # 可选：可执行部分（脚本 / 命令 / MCP 服务）
permissions: ...   # 它需要的权限，见原则 5
---
正文：用法、注意事项、判断标准（被调用时才加载进上下文）
```

| 深度 | 例子 | 写法 |
|---|---|---|
| 纯指引 | testing、debugging | 只有正文 |
| 指引 + 外部执行 | 跑 lint 并总结、查 Jira | 正文 + `run:`，或指向 MCP 服务 |
| 原生 | `edit_file`、`write_file`、`bash` | TypeScript 实现，用同一种声明格式暴露 |

- 新能力不用改核心，放一个文件即可；用户和项目可以自己加、可以分享。
- MCP 是 `run:` 的一种后端，不是另一个子系统。
- 渐进披露：常驻上下文的只有一行 description，正文按需加载。
- 工具声明不再散落在一个大 switch 里，名字写错也不会静默落到默认值。

### 4. 不变量归能力自己

- 一个能力自己保证它的不变量。例如 `edit_file` 自己保证"读过才能改、文件没变才能改"，核心不知道、也不该知道这件事。
- 核心只提供**原语**，不规定用法：会话级、按能力命名空间隔离的状态存储，跨进程锁服务，取消信号，路径解析。
- 共享不变量的能力成组发布（`read_file` 记录版本，`edit_file` 检查）。原生文件工具作为一个整体包，不允许只覆盖其中一个。
- 同名时，项目级可以新增能力，不能覆盖原生能力。

### 5. 权限由用户授予，而不是按来源划分信任

- 每个能力声明自己需要什么权限，例如：文件读写范围、网络域名、执行进程、读取环境变量或密钥、启动子 agent。
- 第一次使用时向用户展示权限清单，用户同意才生效。来源（内置、用户、项目、第三方）不决定信任，用户的同意才决定。
- **核心只做一件事：强制执行用户批准过的权限。** 这也是路径边界、symlink 防护这类全局检查的归属。
- 授权是上限；Agent Spec 的 `tools:` 只能在上限之内收窄，不能放宽。
- 授权记录存在用户级文件（例如 `~/.coder/grants.json`），按"能力 + 内容哈希"记录，不跟着项目走，所以陌生仓库无法自带授权。
- 权限清单变化时必须重新同意，不静默继承。
- yolo 模式就是"全部授权"，不增加摩擦。
- **诚实的限制：** 对 `run:` 外部进程，声明不等于强制。能执行进程就几乎等于全部权限，展示给用户时必须如实说明，除非将来加沙箱。
- 权限的粒度先粗后细，避免用户被点同意淹没。

### 6. 可信：完成必须有证据

- 能力的前提是结果靠得住。声称完成之前，要能指出验证过什么：文件读回、测试结果、命令退出码。
- 没有成功的工具结果，就不能说"已保存""已修复"。
- **这条由谁来守，待定。**
  - 方案 A：写文件的能力自己读回验证（符合原则 4）。
  - 方案 B：需要某个跨能力的检查，因为"agent 在回答里声称完成"不属于任何单个工具。

### 7. 用数据说话

- 没有基线数据的"改进"，不算改进。
- 工具、prompt、文档、上下文策略的改动，都应该能在评测里看到效果。
- 这是"厚工具、厚文档"路线的前提：没有评测，就无法知道哪段文档有用、哪个复杂工具值得。
- 落地手段：会话采用只追加的事件日志，并保证"模型可见的内容都已记录、每个模型请求都能从日志重建"，这样任何一次任务都能回放、对比、做失败分类。（借鉴 DeepSeek Harness 的 session log。）

### 8. 防 agent 犯错，不防用户

- 不加确认弹窗，用户运行 yolo 就是 yolo。
- 对意外破坏做硬防护：覆盖未读过的文件、并发写冲突、会话丢失。这些由对应能力自己保证（原则 4），权限边界由核心执行（原则 5）。

## 原则冲突时

- **能力 > 简单。** 简单只是手段。某个复杂度如果确实带来可验证的能力提升，就值得加，但要用最简单的方式实现。
- **可信 > 灵活。** 为了让结果可信而必须保证的检查，不留给 spec 绕过。

## 谁负责什么

| 核心 | 能力（工具 / skill） | 文档 / spec |
|---|---|---|
| agent loop、调度、mailbox | 自己的不变量（读后才能改、原子写） | agent 的角色和职责 |
| 会话与实例的持久化、崩溃恢复 | 内部的容错与回退 | 使用哪个模型 |
| 并发、超时、递归深度上限 | 声明自己需要的权限 | 何时委派、是否并行 |
| 强制执行用户批准的权限 | 通用原语的使用方式 | 调试、测试、git 等工作方法 |
| 提供通用原语（状态存储、锁、取消、路径解析） | | 可见能力的子集（只能收窄） |

核心里不出现具体工具的语义，也不出现 router、planner 之类的角色语义。

## 已知偏差

- `ToolExecutionContext`（`src/tools/types.ts`）里有 `requirePriorRead`、`getReadVersion`、`recordReadVersion`、`recordWriteVersion`，是 `read_file` 与 `edit_file` 的私有约定，却写进了核心的通用类型。应改为通用的命名空间状态存储。
- `src/infra/tools.ts` 是一个 1692 行的 switch，工具声明和实现没有分开，名字写错会落到 `{effect:'read'}` 兜底。
- `agents/main.md` 里的硬保证（如"写完必须读回验证"）只靠 prompt 约束，项目级 spec 整体覆盖后会丢失。归属取决于原则 6 的决定。
- 路径边界目前是在工具执行出口做的统一检查，没有和"用户授予的权限"关联。

- 怎么评测"文档改动"的效果？需要什么样的任务集？
